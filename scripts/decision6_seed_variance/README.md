# Multi-Seed Variance: scripts

This work repeats each already-tuned model's final fit across multiple random seeds (5
generally, 3 for F-DATA RandomForest specifically, given its cost) to test whether a "best
model" claim is robust to seed-to-seed stochasticity, rather than an artifact of a single
lucky/unlucky fit -- followed by paired significance testing on the resulting winner
(notebook `08`). This README and the scripts below are written to stand on their own;
`EXPERIMENT_TRACKER.md` (a personal/gitignored working file, not part of this repo's committed
history) has additional day-by-day narrative detail but is not required to understand any of this.

These are the scripts that produced every result documented in
`notebooks/05d_seed_variance.ipynb`, plus the two
"Phase 3" pipeline rebuilds (F-DATA power, PM100 duration) that produced the canonical
single-seed numbers baked into `notebooks/05c_classical_ml_power_duration.ipynb`. They were
moved here from a session scratch directory (`/tmp/...`) with their hardcoded paths fixed;
nothing about what they compute has changed. Seed-level R² values, along with every other
metric from every combination this project has produced, now live in the single project-wide
results ledger built by [`scripts/build_results_ledger.py`](../build_results_ledger.py) -- see
that script's own docstring for how it sources and verifies each value.
[`results/seed_variance.csv`](../../results/seed_variance.csv) is a filtered view of that
ledger (regenerated by the same script), not a separately maintained file.

## Why these exist / why they're structured as one-fresh-process-per-model

The first F-DATA power attempt (single long-lived kernel running RF -> XGBoost -> LightGBM
in sequence) hit a genuine ~30-hour Linux OOM crash, root-caused to wasted LightGBM boosting
rounds (no early stopping) stacking on top of an already-large (~85GB) resident process
holding the full 16.3M-row train split. The fix was architectural: **one fresh `uv run`
process per model**, each loading only what it needs from a `joblib`-dumped prepared-data
file, with early stopping added to XGBoost/LightGBM's Optuna objectives. `fdata_power_crash_investigation/`
holds the two scripts (`lgbm_earlystop_test.py`, `lgbm_earlystop_expensive_test.py`) used to
verify the early-stopping fix in isolation before trusting it in the real pipeline; they are
not part of the run order below and don't need to be re-run.

This is also part of why `tree_method="hist"` vs `"exact"` shows up throughout: a real,
reproducible XGBoost bug was found on F-DATA power's feature set where `hist`/`approx`
catastrophically underfit (R²≈0.31) while `exact` recovered full accuracy (R²≈0.99) -- isolated
via elimination (not hyperparameters, not float32/64 precision, not the embedding-PCA columns)
to something in XGBoost's histogram-binning algorithm specifically on this feature set.
Established practice from that point on: tune with `hist` (fast), then check `exact` at the
final fit and use whichever is empirically better, disclosed either way.

## Required launch pattern: `systemd-run --user --scope`, never bare background/`setsid`

Every long-running script here was launched with:

```bash
systemd-run --user --scope --unit=<some-unique-name> -- /path/to/wrapper.sh
```

**Do not launch these with `nohup ... &`, `disown`, or bare `setsid`.** In this environment,
a `setsid`-detached process passes every standard "is it really detached" check (`PPID=1`, its
own session ID) but still gets auto-adopted by `systemd-logind` into an ephemeral
`session-N.scope` cgroup, and those cgroups get cycled/torn down independent of any one
conversation's own teardowns -- a multi-hour fit can silently die partway through with no error
surfaced. `systemd-run --user --scope` places the process under the stable `user@1000.service`
branch instead, which was confirmed immune to this across dozens of teardown events during the
original multi-seed variance work.

**Each `.sh` wrapper needs a real script file, not a one-line inline `systemd-run ... --
uv run python script.py`.** Passing `--working-directory=.../notebooks` directly to
`systemd-run` does not reliably propagate to the child `uv`/`python` process's actual cwd, and
the scripts below all do `from src import ...`, which only resolves with `notebooks/` as cwd
(via `sys.path.append("..")` at the top of each script). Every wrapper here derives its own
paths from its own location rather than hardcoding an absolute path to this machine's clone:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJ="$(cd "$SCRIPT_DIR/../.." && pwd)"
cd "$PROJ/notebooks"
```

(`SCRIPT_DIR` is this directory, `PROJ` is two levels up -- the repo root -- computed at
run time from wherever the wrapper actually lives, not written in as a literal
`/home/bizon/...` path.) This is why the wrappers can be run with any absolute or relative
path to the script itself, from any cwd, and still work after a `git clone` to a different
machine or directory. Keep this pattern if you copy it elsewhere.

Example, to re-run the F-DATA power seed sweep:

```bash
systemd-run --user --scope --unit=fdata-power-seedvar -- \
    /path/to/hpc-dl-enhanced/scripts/decision6_seed_variance/run_fdata_power_seedvar.sh
```

Then tail its output via `journalctl --user -u fdata-power-seedvar -f`, or redirect stdout
inside the wrapper if you want a plain log file.

## Must run with `notebooks/` as the working directory

All Python scripts here begin with `sys.path.append("..")` and load data via relative paths
like `../data/raw/...` and `../data/interim/...`. They must be run from `notebooks/` as cwd --
either via one of the `.sh` wrappers (which `cd` there via the derived `$PROJ/notebooks`, not
a hardcoded path) or manually, substituting your own clone's path for the example below:

```bash
cd /path/to/hpc-dl-enhanced/notebooks
uv run --project /path/to/hpc-dl-enhanced python -u \
    ../scripts/decision6_seed_variance/fdata_power_seed_rf.py
```

## Run order

Each numbered stage below is a `run_*.sh` wrapper that chains its stage's scripts in one
`systemd-run` unit. `*_00_setup.py` scripts build and `joblib.dump` the prepared feature
matrix (`data/interim/*_prepared.joblib`) each combination's later stages load -- these already
exist in this repo's `data/interim/` (gitignored) from the original run, so re-running a
`00_setup.py` is only needed if that directory is wiped or you want to reproduce it from raw
data.

| Order | Combination | Wrapper | Notes |
|---|---|---|---|
| 1 | F-DATA power -- original pipeline | `run_fdata_power_pipeline.sh` | Produces the canonical RF/XGBoost/LightGBM fits baked into `05c`. XGBoost's script (`fdata_power_02_xgb.py`) tunes with `hist`, final-fits with `exact` (`fdata_power_02b_xgb_exact_final.py`). |
| 2 | F-DATA power -- seed variance | `run_fdata_power_seedvar.sh` | RF (3 seeds) + LightGBM (5 seeds) + XGBoost 1M-sample check (5 seeds). |
| 2b | F-DATA power -- XGBoost full-scale escalation | `run_fdata_power_xgb_fullscale_seedvar.sh` | Only needed because the 1M-sample sweep came back wide (std 6x the full-scale std); ~59 min/seed. |
| 3 | F-DATA duration (Result 2) -- seed variance | `run_fdata_duration_r2_seedvar.sh` | No saved model objects existed for Result 2; this reconstructs the full pipeline (38-month load, `mszl` fix, window=5/20/50 rolling stats) before sweeping seeds. |
| 3b | F-DATA duration -- hist/exact check | `run_fdata_duration_xgb_histexact_check.sh` | One-point check at `best_params`, seed 0 only; closes the asymmetry with F-DATA power's known bug. |
| 4 | F-DATA memory -- seed variance | `run_fdata_memory_seedvar.sh` | RF (3 seeds) + XGBoost `hist` (5 seeds) + LightGBM (5 seeds). |
| 4b | F-DATA memory -- XGBoost `exact` escalation | `run_fdata_memory_xgb_exact.sh` | Triggered by a real `hist` vs `exact` gap found at seed 0 (0.0354). |
| 4c | F-DATA memory -- seed-4 outlier diagnostic | `run_fdata_memory_xgb_seed4_diagnose.sh` | Investigates why `exact` seed 4 (R²=0.7354) is far below `exact` seed 2 (R²=0.8495); not part of the headline sweep, a follow-up diagnostic only. |
| 5 | PM100 power -- seed variance | `run_pm100_power_seedvar.sh` | RF, LightGBM (5 seeds each), and XGBoost `hist` (a one-point hist-vs-exact check at seed 0 plus the 5-seed `hist` sweep, both inside `pm100_power_seed_xgb.py`). |
| 5b | PM100 power -- XGBoost full `exact` sweep | `pm100_power_seed_xgb_exact.py` (no wrapper -- run directly, given the ~seconds-per-fit cost) | `uv run --project /path/to/hpc-dl-enhanced python -u scripts/decision6_seed_variance/pm100_power_seed_xgb_exact.py` from `notebooks/`. Full 5-seed `exact` sweep, run once `hist` vs `exact` agreed closely enough not to need `systemd-run`. |
| 6 | PM100 memory (clean-4) -- seed variance | `run_pm100_memory_c4_seedvar.sh` | Same clean-4 feature set as the canonical result (`mem_req` deliberately excluded -- see the 2026-09-05 tracker entry). Both `hist` and `exact` in full for XGBoost. |
| 7 | PM100 duration -- original pipeline | `run_pm100_duration_pipeline.sh` | Produces the canonical RF/XGBoost/LightGBM fits baked into `05c`. |
| 7b | PM100 duration -- extended 200-trial check | `run_pm100_duration_ext200.sh` | Bounded investigation pass (not open-ended tuning): confirms the fixed 50-trial Optuna tuning budget (applied equally to every tunable model family, so no model gets a cost advantage) wasn't leaving R² on the table. Came back *worse*, not better -- 50 trials confirmed as final. |
| 7c | PM100 duration -- seed variance | `run_pm100_duration_seedvar.sh` | RF, XGBoost (`hist` and `exact` both, in full), LightGBM; all 5 seeds. |

None of the scripts in this directory write `results/seed_variance.csv` directly. That file,
along with `results/results_ledger.csv` and `results/tuning_details.csv`, is generated by
`scripts/build_results_ledger.py` (not part of the run order above -- it's a plain read of the
already-saved `.joblib` files and committed notebook outputs, no `systemd-run` needed, runs in
seconds). Run it with:

```bash
uv run python scripts/build_results_ledger.py
```
